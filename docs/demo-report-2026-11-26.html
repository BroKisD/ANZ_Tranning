AI App Builder Demo Report

A user's request becomes a GitHub repository, a pull request, a human approval, and a live app on Google Cloud Run. This report shows how the demo works today, how to set it up, and what stands between it and a real product.

The happy path

Twelve messages between five parties. The amber dashed boxes are mocked, everything else is a real call.

What the API shows along the way

Poll GET /api/projects/{id}. The two fields status and current_step move like this:

pending→ generating · repo_created→ generating · tests_passed→ waiting_for_approval→ deploying · merging→ deploying · merged→ deploying · building→ deploying · testing→ deploying · deploying→ success + live_url

Any error ends in failed with an error_message. A deploy that goes silent for 15 minutes is failed by a watchdog.

Inside the GitHub Actions run

The repo's deploy.yml starts on a push to main (the PR merge) or by hand (workflow_dispatch, used for re-deploys). A newer run cancels an older one for the same repo.

Prepare notifierWrites a small notify helper that posts JSON to the webhook. A failed post only prints a warning.none

The infrastructure files that are committed into every new repo are .github/workflows/deploy.yml and service.yml (the Cloud Run spec). The platform restores both from the base branch before opening the PR, so generated code cannot change the pipeline.

How to set it up

A

GitHub

Personal access token
  • Classic token with the repo and workflow scopes. workflow is needed to commit the deploy workflow into a new repo.
  • The platform stores it encrypted (AES-256-GCM) per user.
The code to deploy
  • The demo clones this repo (DEMO_TEMPLATE_REPO). It must be public, and your latest changes must be pushed to main.
  • No GitHub App is needed.
B

Google Cloud (one time)

Project project-9991dcfb-85ec-4182-b68, region asia-southeast1, Artifact Registry repo anz-repo, deploy service account anz-trainning@… (the one the existing CI/CD already uses).

The commands below assume P=project-9991dcfb-85ec-4182-b68.

1. Let the Workload Identity provider accept every repo of the GitHub account, not only one repo:

gcloud iam workload-identity-pools providers update-oidc github-provider \
  --project=$P --location=global --workload-identity-pool=github-pool \
  --attribute-mapping="google.subject=assertion.sub,attribute.repository=assertion.repository,attribute.repository_owner=assertion.repository_owner,attribute.actor=assertion.actor" \
  --attribute-condition="assertion.repository_owner=='BroKisD'"

2. Let those repos impersonate the deploy service account:

gcloud iam service-accounts add-iam-policy-binding \
  anz-trainning@$P.iam.gserviceaccount.com \
  --role=roles/iam.workloadIdentityUser \
  --member="principalSet://iam.googleapis.com/projects/386127327935/locations/global/workloadIdentityPools/github-pool/attribute.repository_owner/BroKisD"

3. Create the webhook secret the platform reads, and let its service account access it:

openssl rand -hex 32 | gcloud secrets create WEBHOOK_SECRET --data-file=- --project=$P
C

The platform on Cloud Run

service.yml describes it and the existing ci-cd.yml deploys it on every push to main. Three settings are required by design:

  • minScale: 1 and maxScale: 1, because each run lives in a background goroutine and the approval wait is held in memory.
  • cpu-throttling: "false", so that background work keeps its CPU between requests.
  • WEBHOOK_URL set to the service's own address, which is predictable: https://<service>-<project number>.<region>.run.app/api/webhooks/github.
SettingValue
DEMO_TEMPLATE_REPO + GCP_PROJECT_IDTogether they switch on deploy mode.
GCP_WIF_PROVIDER, GCP_SERVICE_ACCOUNTThe deploy identity from step B. The workflow receives these two values.
GCP_ARTIFACT_REPO, GCP_REGIONanz-repo, asia-southeast1

D

Run the demo

One command creates a real repo, opens a PR, approves it, watches the Actions run step by step and checks that the live URL answers 200. It needs no server and no Postman.

LIVE_DEPLOY=1 GITHUB_TOKEN=ghp_... \
  go test ./test -run TestLive_Deploy -v -timeout 20m

To drive the deployed platform over HTTP instead, use TestLive_Platform with PLATFORM_URL, API_KEY and GITHUB_TOKEN. The manual route is: create a user, connect GitHub (POST /api/integrations/github), POST /api/projects, poll, POST /api/projects/{id}/approve.

Problems we hit while setting it up

Each one is a one-time setup issue, not a code bug, and each is now written into docs/deploy-setup.md.

The given credential is rejected by the attribute condition.

The existing provider only trusted the single repo BroKisD/ANZ_Tranning. Fixed by widening its condition to every repo owned by the account (step B1).

Permission 'iam.serviceAccounts.getAccessToken' denied

The login worked, but the deploy service account did not trust the new repo. Fixed by the owner-wide binding (step B2).

The user-provided container failed to start and listen on the port defined by PORT=8080

The demo deploys a clone of this repo, which needs a MySQL database to start, and Cloud Run has none for it. Fixed by a standalone mode: with no database settings the app serves a small status page. The fix also had to be pushed to GitHub, because the clone comes from there.

Evidence

Live run

On 25 November the full flow ran against real GitHub and Cloud Run and ended with a live app. The three setup errors above were the only failures before it.

Still to confirm: the same flow through the deployed platform's own API with the real webhook (TestLive_Platform), and the platform's new container image running on Cloud Run.

Automated tests

  • 106 test functions: 100 run by default, 3 live tests opt in, 3 database tests need Docker.
  • Run with the race detector, go vet clean.
  • Google Cloud and GitHub are replaced by fake servers, so the checks run without credentials.
  • Covered: approval gate, webhook security, forward-only status, watchdog, re-deploy rules, workflow and service file generation, IAM retry and idempotency.

Independent review

A fresh reviewer read the whole change and reported 15 findings: 2 critical, 6 important, 7 minor. Seven were fixed with a failing test first, one is documented as an accepted limit (below), and the minor ones are deferred.

Fixed among them: apps no longer run as the platform's identity in the self-provisioning mode, a never-merged project can no longer be re-deployed, and a late success after a watchdog failure is accepted.

Suggested order of work

  1. Real sign-in and per-user checks. This closes the largest security hole and is small.
  2. Move generated apps to their own Google project, with a role-less runtime account per app.
  3. Replace the personal token with a GitHub App.
  4. Run the project's real tests and builds in Actions, and surface the logs through the API.
  5. Turn the Claude Code generation path on in a sandbox, behind the same approval gate.
  6. Make runs durable (queue or workflow engine), then add delete, rollback, quotas and a dashboard.
